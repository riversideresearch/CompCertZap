# Domain Pitfalls: Coq Proof Cleanup in CompCert

**Domain:** Refactoring and cleanup of CompCert-style formally verified compiler proofs
**Researched:** 2026-03-03
**Confidence:** HIGH (all findings grounded in this codebase's actual source files)

---

## Critical Pitfalls

Mistakes that cause build failures, introduce `Admitted`, or silently weaken theorems.

---

### Pitfall 1: Removing a Lemma That Still Has Call Sites

**What goes wrong:** The old `external_call_Three_Two` lemma in `RTLtolerant.v` is marked TODO for removal, but it has three active call sites (lines 1706, 1766, 1856) that must be migrated to `external_call_Three_Two'` first. Deleting the lemma without migrating call sites breaks the build immediately.

**Why it happens:** In large proof files (2849 lines for `RTLtolerant.v`) it is easy to delete the named lemma after finding it, without searching the rest of the file for uses. The presence of the commented-out *earlier* version of the same lemma (lines 1152–1162) suggests this file has already been partially reorganized and old/new names coexist.

**Consequences:** `make backend/RTLtolerant.vo` fails; downstream `make proof` fails.

**Prevention:**
- Before removing any lemma, run `grep -rn "<lemma_name>" backend/ driver/` to enumerate all call sites.
- In the same commit that removes the old lemma, update all call sites to the replacement.
- Never split "remove old" and "update callers" across two commits.

**Detection:** `make backend/RTLtolerant.vo` immediately reports `Error: The reference external_call_Three_Two was not found`.

**Phase:** Phase 2 (De-duplicate proof scripts).

### Pitfall 2: Splitting a File Without Updating the Makefile and `_CoqProject`

**What goes wrong:** The plan introduces two new files: `backend/RTLreplicateSpecCommon.v` and `backend/RTLreplicateProofCommon.v`. These files must be added to the `BACKEND` variable in `Makefile` (around line 166) and to `_CoqProject` (which is auto-generated by `make` from `COQINCLUDES`). If they are created but not registered, `Require Import RTLreplicateSpecCommon` in other files will fail with a module-not-found error.

**Why it happens:** `_CoqProject` is generated (see `.gitignore` entry `/_CoqProject`) so it is invisible until `make` runs. The Makefile's `BACKEND` variable controls which `.v` files get compiled; missing entries silently skip compilation. This is not obvious from the file-creation step alone.

**Consequences:** New files compile in isolation but cause build failures when imported. Downstream files that `Require Import RTLreplicateSpecCommon` fail.

**Prevention:**
- Add the new filename to `Makefile` line 166 in the same commit that creates the file.
- Run `make backend/RTLreplicateSpecCommon.vo` immediately after creation to confirm the build system picks it up.
- Regenerate `_CoqProject` with `make` before invoking IDE tooling.

**Detection:** `Error: Cannot find library RTLreplicateSpecCommon` during `make`.

**Phase:** Phase 1 (File and module reorganization).

### Pitfall 3: Moving Lemmas Out of a Coq `Section` Changes Their Types

**What goes wrong:** Both `RTLtmrproof.v` and `RTLdmrproof.v` wrap all content in `Section VOTE` with `Context {VT: vote_type} {vsem: VoteSemantics VT}` (lines 28–31 in each file). When a lemma is extracted to a new shared file (`RTLreplicateProofCommon.v`), the section context is no longer in scope. Every lemma that referred to `VT` or `vsem` implicitly now requires explicit universally quantified or typeclass parameters added to its signature.

**Why it happens:** Coq sections discharge variables automatically at `End`; moving a definition outside a section forces all implicit section variables to become explicit parameters. This is not a semantic change — the lemma is still true — but it changes the type that callers see, so all `apply` / `eapply` call sites may need updating.

**Consequences:** Callers in `RTLtmrproof.v` and `RTLdmrproof.v` that `apply SharedLemma` now see a type mismatch or unsatisfied implicit argument; `make` fails with unification errors.

**Prevention:**
- After moving a lemma, immediately verify the extracted lemma's type with `Check <lemma_name>.` in the new file.
- Compare that type against what callers expect — if the new type has extra parameters, update every call site.
- Run targeted `make backend/RTLdmrproof.vo backend/RTLtmrproof.vo` before committing.

**Detection:** `Error: Illegal application` or `Unable to unify ... with ...` at old call sites after the move.

**Phase:** Phase 1 (introducing shared modules).

### Pitfall 4: Accidentally Weakening a Theorem Signature While Resolving a TODO

**What goes wrong:** `CSEproof.v` line 1574 has a TODO to add `Novotes` as an explicit hypothesis to `transf_program_correct`. The theorem is currently:

```
Theorem transf_program_correct :
  forward_simulation (RTL.semantics prog) (RTL.semantics tprog).
```

If the cleanup adds `Novotes.no_votes prog` as a new hypothesis, `driver/Complements.v` which chains this theorem into the pipeline must be updated simultaneously. If `Complements.v` is not updated, Coq will silently accept the change (the weaker hypothesis is now just an assumption not discharged in the pipeline proof), and the top-level preservation theorem in `Complements.v` will have an undischarged `no_votes prog` precondition that was not there before.

**Why it happens:** Theorem signature changes in intermediate passes do not always cause build failures — they just change what preconditions callers must supply. If a caller already has `no_votes` available (as `Complements.v` does, via `transf_c_program_to_rtl'_no_votes`), the build may pass, but the *logical* structure of the composed proof changes in ways that might not be intended.

**Consequences:** The top-level theorem silently gains a new precondition that was not reviewed or intended by the caller.

**Prevention:**
- Before changing any theorem signature, audit every call site with `grep -rn "<theorem_name>"`.
- Document the intended signature change in the commit message and confirm with `make check-admitted`.
- Prefer Option B from the TODO comment (use the existing `Novotes.check_program` checker soundness to discharge the hypothesis inside the CSE proof, not as an external precondition).

**Detection:** `make proof` succeeds, but `make check-admitted` or manual inspection of `Complements.v` reveals new unproved side conditions.

**Phase:** Phase 4 (`no_votes` policy alignment).

### Pitfall 5: Leaving a Commented-Out `Admitted` That Confuses `make check-admitted`

**What goes wrong:** Several files contain commented-out proof drafts with `admit` or `Admitted` inside comments (e.g., `RTLagreement.v` lines 102–137, `Novotesproof.v` line 234, `Complements.v` line 284). The tool `make check-admitted` scans for the string "Admitted" — whether or not it is inside a comment is irrelevant to a naive grep. A cleanup pass that "removes commented-out failed proof blocks" might inadvertently also remove the grep targets for `check-admitted`, making the check vacuously pass while active `Admitted`s from other files are missed.

**Why it happens:** `make check-admitted` is a text-scan heuristic, not a Coq semantic check. It can give false confidence.

**Consequences:** Active `Admitted` proofs in untouched files are masked by the false sense of security from a passing `check-admitted` run.

**Prevention:**
- After each phase, run `coqwc` or `grep -rn "^[^(]*Admitted" backend/ driver/` (regex anchored to avoid comment matches) in addition to `make check-admitted`.
- Treat `check-admitted` as a necessary but not sufficient condition.

**Detection:** `grep -rn "^\s*Admitted" backend/ driver/` (no comment prefix) should return zero results in healthy state.

**Phase:** Phase 0 (baseline) and after each phase's integration check.

## Moderate Pitfalls

---

### Pitfall 6: DMR and TMR Shared Lemma Names Collide in the Common Module

**What goes wrong:** `RTLdmrproof.v` and `RTLtmrproof.v` share lemma names (`rm_wf_neq_1_2`, `rm_wf_neq_2_2`, `rm_wf_neq_2_1'`, `rm_wf_neq_2_2'`, `match_regsets_get_2`, `rs_args1_rs'_args2`, etc.) but with different types — DMR uses `PMap.t reg` (one replica register) while TMR uses `PMap.t (reg * reg)` (two replica registers). Placing both in a single `RTLreplicateProofCommon.v` without namespacing will produce name conflicts.

**Why it happens:** The lemma names look parallel and tempt a naive copy-paste merge, but the types are genuinely different and cannot be unified without a typeclass or parametric definition over DMR/TMR replication arity.

**Consequences:** Coq name collision error or, worse, one version silently shadows the other in downstream `Require Import` chains.

**Prevention:**
- Use Coq modules or separate namespaced sections within the common file (`Module DMRCommon.` / `Module TMRCommon.`), or keep separate files `RTLdmrProofCommon.v` and `RTLtmrProofCommon.v` that both depend on a shared base of truly arity-independent lemmas.
- Only put lemmas into the common file that have *identical* types modulo the replication map type.

**Detection:** `Error: <lemma_name> already exists` during `make`.

**Phase:** Phase 1 (shared helper modules).

### Pitfall 7: Refactoring `maj_voteR_step` Four-Case Proof Breaks Architecture Dispatch

**What goes wrong:** The four-case duplication in `RTLtmrproof.v` `maj_voteR_step` (line 772) exists because each case dispatches on a different `ty` constructor (`Tint`, `Tfloat`, `Tlong`, `Tsingle`) and calls a distinct lemma (`vote_sem_int_ok`, `vote_sem_float_ok`, etc.) from the `VoteSemantics` typeclass instance. A refactor that introduces a parametric helper must be careful not to collapse the cases in a way that prevents `destruct vsem` from reducing.

**Why it happens:** The `VoteSemantics` typeclass has per-type fields. Any generic lemma over all types must either quantify over the type and carry the appropriate field as a hypothesis, or use a tactic that re-performs the case split internally. Naive abstraction with `destruct ty` inside a new helper lemma re-introduces the same four cases inside the helper.

**Consequences:** The refactored proof is no longer shorter; the four cases just moved inside the helper. Or, if the helper is too abstract, the `vote_sem_*_ok` lemmas don't reduce and the proof fails.

**Prevention:**
- The correct abstraction is a lemma parameterized by `(vote_ok : Val.has_type v ty -> vote_sem ...)` — a function argument, not a type dispatch. Check that this approach compiles before declaring the refactor complete.
- Run `make backend/RTLtmrproof.vo` after each attempted reduction.

**Detection:** Proof still has `destruct ty` in the new helper, or `make backend/RTLtmrproof.vo` fails.

**Phase:** Phase 2 (de-duplicating proof scripts).

### Pitfall 8: Deleting Backup Files That Contain the Only Copy of a Committed Idea

**What goes wrong:** Files like `backend/DMRproof_backup.v`, `backend/DMRproof_backup2.v`, `backend/RTLfault_backup.v`, `backend/RTLAgreement_backup.v`, and `driver/backup_Compiler.v` are untracked by git. They are not in the build, and no active `.v` file imports them. They appear safe to delete. However, they may contain proof techniques, intermediate lemma ideas, or commented-out strategies not captured elsewhere — including failed `Admitted` proofs that document *why* a particular approach was abandoned.

**Why it happens:** During active proof development, backup files serve as a scratchpad. Their absence from git does not mean their content is worthless.

**Consequences:** Discarding context that would inform future proof decisions, leading to re-exploration of abandoned paths.

**Prevention:**
- Before deletion, skim each backup file for any comments, lemma statements, or proof strategies not present in the current active files.
- If anything valuable is found, extract a comment into the corresponding active file before deleting the backup.
- Then delete and commit.

**Detection:** A future developer re-discovers the same failed approach that was documented only in the deleted backup.

**Phase:** Phase 1 (file and module reorganization).

### Pitfall 9: Splitting `RTLtolerant.v` Without Respecting Mutual Definitions

**What goes wrong:** The plan to split `RTLtolerant.v` (2849 lines) into focused modules (match relations, helper lemmas, main simulation theorem) must account for mutual dependencies: `match_rs` uses `color`, `match_states` uses `match_rs`, and the simulation relation uses `match_states`. In Coq, these must appear in dependency order in a single file or in separate files where later files `Require Import` earlier ones.

**Why it happens:** Splitting a large file into multiple smaller files in Coq is not like splitting a module in Python — circular `Require Import` is not allowed. If `A.v` and `B.v` mutually depend on definitions from each other, there is no way to separate them without a third file `C.v` containing the shared base.

**Consequences:** A circular import error forces a redesign of the split boundary after the work is already done.

**Prevention:**
- Before splitting, draw the dependency graph of definitions within `RTLtolerant.v`. Confirm all edges are acyclic across the proposed file boundaries.
- The split order must be: shared definitions (colors, regsets) → helper lemmas → simulation theorem.

**Detection:** `Error: Require Import creates a dependency cycle` during `make`.

**Phase:** Phase 2 (file splitting of `RTLtolerant.v`).

## Minor Pitfalls

---

### Pitfall 10: Tactic Hygiene Changes Break `Proof. ... Qed.` Boundaries

**What goes wrong:** Phase 5 replaces broad `inv`/`try solve` clusters with named local tactics. In Coq, `Ltac` definitions inside a proof (`ltac: (...)`) have different scoping than top-level `Ltac` or `Tactic Notation`. Introducing a local tactic in one lemma and then applying it in a later lemma in the same file requires the tactic to be at file scope, not inside a `Proof ... Qed` block.

**Prevention:** Define shared tactics at file scope, above the first lemma that uses them. Verify with `make backend/<file>.vo` that the tactic is visible at all use sites.

**Phase:** Phase 5 (comment and tactic hygiene).

---

### Pitfall 11: The `no_votes` Policy Decision Has Unresolved Design Conflict

**What goes wrong:** `RTLagreement.v` lines 139–163 contain two mutually contradictory design notes: one argues for moving `no_votes` to an RTL-level pass checker (Option B), and an addendum argues that `no_votes` may not even be needed. Phase 4 must resolve this conflict with a single decision before touching `CSEproof.v` or `Complements.v`. If Phase 4 is executed while this ambiguity is unresolved, cleanup of one file may be invalidated by a subsequent decision about the other file.

**Prevention:** Decide Option A or Option B before any Phase 4 code changes. Record the decision in a commit message or the TODO closure comment.

**Detection:** The comment block at `RTLagreement.v:139` and the conflicting addendum at line 149 remain both present after Phase 4 work has started.

**Phase:** Phase 4 (`no_votes` policy alignment).

---

### Pitfall 12: `check_col_instr_sound` Split Breaks Boolean Reflection Lemma Chain

**What goes wrong:** `RTLcolorcheck.v` uses `reflect`-style Boolean lemmas (`is_basicb_spec`, `is_basicb'_spec`) that serve as bridges between the Boolean checker and the propositional color spec. `check_col_instr_sound` is a single large proof that chains these reflect lemmas. Splitting it into per-instruction lemmas is correct in principle but requires each sub-lemma to carry the full set of hypotheses currently held in the outer proof context.

**Prevention:** Extract one per-instruction lemma at a time, verify with `make backend/RTLcolorcheck.vo` after each extraction, and confirm the outer proof still closes by using the new sub-lemma.

**Phase:** Phase 2 (de-duplicating `RTLcolorcheck.v`).
