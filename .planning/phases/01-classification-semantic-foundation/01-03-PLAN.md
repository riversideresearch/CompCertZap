**Approach for mkbuiltin_nNt builtins:**

The key insight is that mkbuiltin_nNt builtins go through `proj_num`/`inj_num`. Under `val_compat`:
- If inputs have the same constructor (e.g., both Vfloat), `proj_num` succeeds on both and the pure function is applied, producing the same output constructor
- If an input is Vundef, `proj_num` returns the default value, and both sides get Vundef output
- If input constructors don't match the expected type, `proj_num` returns the default

A general helper lemma is the cleanest approach:

```coq
(* Helper: val_compat is preserved through proj_num *)
Lemma val_compat_proj_num_1 (t: typ) (v1 v2: val)
  (A: Type) (f1 f2: valty t -> A) (d: A) (inj: A -> val) :
  val_compat v1 v2 ->
  (forall x y, val_compat (inj (f1 x)) (inj (f2 y))) ->
  val_compat (inj d) (inj d) ->
  val_compat (proj_num t (inj d) v1 (fun x => inj (f1 x)))
             (proj_num t (inj d) v2 (fun x => inj (f2 x))).
```

Then prove per-builtin lemmas or a unified lemma. The simplest approach:

Prove a lemma for each class of standard_builtin_sem output:
1. 1-argument mkbuiltin_n1t (BI_fabs, BI_fabsf, BI_fsqrt, BI_negl, BI_i16_bswap, BI_i32_bswap, BI_i64_bswap, BI_i64_stod, BI_i64_utod, BI_i64_stof, BI_i64_utof): single proj_num -> inj_num
2. 2-argument mkbuiltin_n2t (BI_i64_umulh, BI_i64_smulh, and platform BI_fmin, BI_fmax): nested proj_num -> inj_num

The unified statement should be:
```coq
Lemma builtin_sem_val_compat_nNt (sb: standard_builtin) (vargs1 vargs2: list val) (vres1: val) :
  (* Gate: only for builtins that are mkbuiltin_nNt type *)
  Forall2 val_compat vargs1 vargs2 ->
  standard_builtin_sem sb vargs1 = Some vres1 ->
  exists vres2,
    standard_builtin_sem sb vargs2 = Some vres2 /\
    val_compat vres1 vres2.
```

This is a large case analysis. It may be more tractable to prove it per-builtin or in small groups. Use the rocq-agent MCP for interactive proof development.

**Critical:** The `VoteSemantics` typeclass context is needed for `standard_builtin_sem`. Ensure the lemma is in a Section with appropriate Context, or use explicit quantification: `forall {VT: vote_type} {vsem: VoteSemantics VT}`.

For the proof, the pattern for each mkbuiltin_nNt case is:
1. Unfold `standard_builtin_sem`, reduce to `bs_sem`
2. Destruct vargs1 to get the right number of arguments
3. Invert `Forall2 val_compat` to get val_compat on each argument pair
4. Invert each `val_compat` hypothesis
5. Simplify `proj_num` / `inj_num` applications
6. Show the output exists and is val_compat (same value constructor)

If the unified lemma is too large, split into `builtin_sem_val_compat_n1t` (1-arg) and `builtin_sem_val_compat_n2t` (2-arg).

**For BI_addl, BI_mull, BI_subl:**

These have clean proofs that lift existing val_compat helper lemmas. The pattern:

```coq
Lemma builtin_sem_val_compat_addl vargs1 vargs2 vres1 :
  Forall2 val_compat vargs1 vargs2 ->
  standard_builtin_sem BI_addl vargs1 = Some vres1 ->
  exists vres2,
    standard_builtin_sem BI_addl vargs2 = Some vres2 /\
    val_compat vres1 vres2.
Proof.
  intros Hcompat Hsem.
  simpl in *.
  destruct vargs1 as [|v1 [|v2 [|]]]; try discriminate.
  inv Hcompat. inv H3.
  inv Hsem.
  eexists; split; [reflexivity|].
  apply val_compat_addl; auto.
Qed.
```

Similarly for BI_mull (using val_compat_mull -- note: BI_mull uses Val.mull' not Val.mull, check if val_compat_mull covers Val.mull') and BI_subl (using val_compat_subl, but only when Archi.ptr64 = false per CLAS-07).

For BI_subl: The builtin is only classified as safe when `negb Archi.ptr64 = true` (i.e., `Archi.ptr64 = false`). The val_compat_subl lemma should be sufficient for this case because when ptr64 = false, Val.subl does not involve pointer subtraction. The lemma can either assume `Archi.ptr64 = false` as a hypothesis or be unconditional if val_compat_subl already handles all cases.

**For BI_i64_shl, BI_i64_shr, BI_i64_sar (SHIFT BUILTINS):**

RESEARCH FINDING: These builtins have a genuine val_compat issue. When both arguments are registers and the shift amount can be faulted, `Int.ltu` may succeed on one side and fail on the other, producing `Vlong` vs `Vundef`. Since `val_compat (Vlong x) Vundef` is NOT a constructor, the general val_compat monotonicity does NOT hold for shifts with faulted shift amounts.

**Strategy for shifts:** Attempt the proof. If it does not close:
1. Prove the property for the restricted case where the shift amount is the SAME on both sides (using existing val_compat_shll_imm pattern): `Lemma builtin_sem_val_compat_shl_imm vargs1 vargs2 vres1 : Forall2 val_compat vargs1 vargs2 -> ... -> (nth_error vargs1 1 = nth_error vargs2 1) -> ...`
2. Document that the general case fails with a comment explaining the issue
3. Do NOT remove shifts from the whitelist yet -- Phase 3's tolerant proof may only encounter the restricted case

If the proof DOES close (e.g., because the property statement's direction works out), great -- prove it fully.
