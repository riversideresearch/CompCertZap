Create doc/no-novotes-report.md as a standalone technical report. The report must be self-contained (a reader familiar with CompCert and the fault tolerance extension described in doc/fault_tolerance.md should be able to understand it without reading the planning artifacts).

Structure the report with these sections:

**1. Introduction / Summary**
- One paragraph stating what changed: the Novotes checker pass has been removed from the compiler pipeline; a generic RTL3-to-RTL bridge theorem now proves weak agreement unconditionally (for ALL programs, not just no-votes programs); the top-level fault tolerance theorem uses a simplified 2-step behavior composition.
- State that all proofs compile with zero Admitted (two axioms remain in RTLagreement.v, documented below).

**2. Motivation**
- Explain why Novotes was originally needed: the old 4-step composition required a no_votes premise for the RTL2-to-RTL3 step (step 2 below).
- Explain the cost: Novotes added a compiler pass that rejected programs containing vote builtins before TMR insertion (which was always true for well-formed inputs, making it a vacuous check).
- Explain the conceptual problem: the 4-step chain encoded an unnecessary asymmetry -- weak agreement should hold generically, not just for programs without votes.

**3. Before/After Proof Composition (include ASCII diagrams)**

Before (old 4-step chain):
```
C program
  |  (1) standard backward simulation
  v
2-voting RTL (no votes)
  |  (2) weak agreement from no_votes (trivial)
  v
3-voting RTL (no votes)
  |  (3) TMR backward simulation
  v
3-voting RTL+TMR
  |  (4) faulty backward simulation (requires well-colored)
  v
2-voting faulty RTL+TMR
```
Composition: behavior_improves(beh_c, beh_rtl2) via (1), behavior_improves(beh_rtl2, beh_rtl3) via (2), behavior_improves(beh_rtl3, beh_tmr3) via (3), behavior_improves(beh_tmr3, beh_faulty) via (4). Chain via transitivity.

After (new 2-step composition):
```
C program
  |  (1) standard backward simulation: C >= RTL (2-voting)
  v
RTL (2-voting)
  =  RTL3 behaviors are the same as RTL behaviors for well-colored programs
  |  (this step uses wc_rtl3_behavior_in_rtl, not behavior_improves)
  v
RTL+TMR (3-voting)
  |  (2) faulty backward simulation (requires well-colored)
  v
2-voting faulty RTL+TMR
```
Composition: The theorem obtains beh_c from (1), converts RTL3 behaviors to RTL behaviors via wc_rtl3_behavior_in_rtl (behavior equality, not just improvement), then chains with the faulty backward simulation via behavior_improves_trans.

Explain WHY the old step (2) disappeared: the forward simulation RTL3->RTL in RTLagreement.v proves that RTL3 behaviors are refined by RTL behaviors for ALL programs (not just no-votes). For well-colored programs, this strengthens to behavior equality (wc_rtl3_behavior_in_rtl).

**4. The RTL3-to-RTL Bridge (Phase 5)**
- Explain the core insight: RTL3's vote3 produces Vundef (less-defined) where RTL's vote produces a concrete value. This means RTL3 is the "less-defined" semantics, making forward simulation RTL3->RTL natural via Val.lessdef.
- Match relation: regs_lessdef (pointwise Val.lessdef on register maps) plus Mem.extends.
- external_call3 bridge: external_call3 results are matched by external_call results under Val.lessdef, via decomposition through builtin_function_sem3/known_builtin_sem3/replicate_builtin_sem3.
- Result: forward_simulation (RTL3.semantics p) (RTL.semantics p) with no no_votes hypothesis.
- The forward_simulation_behavior_improves corollary gives rtl_weak_agreement' for all programs.
- Key decision: forward simulation RTL3->RTL (not backward RTL->RTL3) because eval_operation_lessdef goes from less-defined to more-defined arguments.

**5. Well-Colored Behavior Identity (Phase 7 gap closure)**
- Explain why behavior improvement is not enough: the top-level theorem needs to compose C >= RTL with RTL3 = RTL and RTL3+TMR >= faulty. The RTL3-to-RTL bridge gives behavior_improves(beh_rtl3, beh_rtl), but composing this with behavior_improves(beh_c, beh_rtl) creates a diamond (two different behaviors both improve from the same source), which behavior_improves_trans cannot resolve.
- Solution: for well-colored programs, RTL3 and RTL have IDENTICAL behaviors (not just improvement). This is wc_rtl3_behavior_in_rtl.
- Proof approach: two axioms in RTLagreement.v:
  - wc_step_identity: if RTL3 steps from a reachable state, then RTL takes the same step with the same trace and successor state.
  - wc_nostep_identity: if RTL3 is stuck at a reachable state, then RTL is also stuck.
- These axioms are backed by the informal color discipline argument: in well-colored programs, vote arguments are always equal at reachable states (Red = Green = Blue copies hold identical values), so vote3(a,a,a) = a = vote(a,a,a), making RTL3 and RTL execute identically.
- The Goes_wrong case was proved by direct state_behaves inversion (not forward_simulation_behavior_improves, which loses behavior equality via classical logic).
- Lifting lemma: wc_star_identity threads reachability through star induction.

**6. Pipeline Changes (Phase 6)**
- transf_rtl_program and transf_rtl_program_to_rtl in Compiler.v no longer apply Novotes.transf_program.
- Pipeline now ends at Unusedglob before TMR insertion (no intermediate Novotes check).
- Novotes.v and Novotesproof.v removed from Makefile build list but kept on disk as reference.

**7. Validation Results (Phase 8)**
- All .vo files compile (make proof succeeds).
- Zero Admitted proofs across all active source files (make check-admitted reports "Nothing admitted.").
- ccomp binary builds (make ccomp) and successfully compiles C programs with -tmr flag.
- No residual Novotes references in active pipeline code (Compiler.v, Complements.v, etc.).
- Two axioms remain in backend/RTLagreement.v (wc_step_identity, wc_nostep_identity); these encode the color discipline invariant and could be fully mechanized in a future effort.

**8. Remaining Axioms**
- List the two axioms with their exact signatures (read from RTLagreement.v).
- Explain the informal argument: for well-colored programs, the color discipline ensures that vote arguments are always triplicated copies of the same value, so vote3 and vote compute the same result.
- Note that full mechanization would require tracking value flow through smove chains in the CFG, which is substantial new infrastructure but does not affect soundness of the overall proof architecture.

**9. Files Changed**
- Table listing each file modified across phases 5-8, with a one-line description of the change.

The report should be written in a clear, technical style consistent with doc/fault_tolerance.md (which uses Coq code blocks, formal notation, and informal explanations). Include Coq code blocks for key theorem signatures where helpful. Total length: approximately 200-350 lines.
